# 记忆系统审查与检索优化（2026-09-18）

审查基线：`e001c368fe4fe143004e1810db78fe9a099e6957`。本次阅读了记忆存储、检索/预算选择、自动摘要维护及提示词调用链；不是对全部宿主、UI 或恢复路径的重新审计。

## 结论与保持的边界

现有设计中的剧情工作区隔离、来源原文保留、归并前乐观校验、正常完成后才归档、每轮冻结提示词计划值得保留。本次不更改文件格式、剧情绑定、WAL、摘要来源可达性或回滚逻辑，不增加依赖，也不调用真实模型或读取用户剧情数据。

本次先落地可通过行为对照验证的改进：BM25 倒排访问、入模正文精确去重与空正文过滤，以及检索参数的有限数值边界。更大的记忆语义重构另列为后续建议，不混入这次补丁。

## 本次修复

### 1. 每个查询词扫描全部文档

位置：[Bm25Index.search](../src/core/bm25.ts)。原实现虽维护文档频率，但每个存在于词典的查询词仍遍历整个 `docs`。设这些查询词有 Q 个、索引文档有 N 条，候选评分访问量为 O(QN)。[MemoryStore.buildIndex](../src/state/memory.ts) 还会纳入活跃摘要可达的归档来源，因此成本不只由活跃记忆条数决定。

改为维护 `term → Set<DocEntry>`，集合大小直接提供文档频率。查询只遍历命中文档引用，避免再次按 id 查文档表。候选评分访问量降为 O(Σ df(term))；最终命中排序仍为 O(H log H)，并没有把全部检索过程变成常数时间。新增、覆盖、删除和 clear 同步维护倒排集合。

BM25 参数、词频/关键词计算、查询去重、时间衰减、data 透传、topK 与同分 id 排序均保持不变。代价是增加与“文档—不同词项”关联数成正比的索引空间；本次没有测量进程峰值内存。共同高频词命中全库时仍需处理全库，不承诺所有查询都大幅变快。

### 2. 重复正文占用预算，空正文阻断兜底

位置：[selectMemoryBodies](../src/core/memoryRetrieval.ts)。原实现直接按条目累加正文预算，有两种可复现问题：

- `['古城', '古城', '盟约']` 在 4 token 正文预算下，只选中两个“古城”，挤掉不同事实“盟约”。
- 超长高相关正文后出现空正文时，空正文被算作已选中条目，导致“没有完整正文时截取首条”的兜底不再执行。

现在跳过纯空白正文；已选中的相同正文只计一次预算，比较时仅忽略首尾空白。保留首个真正选中条目的原始格式，不修改输入，不删除或合并存储记录。未装入预算的超长条目不会提前占住去重标记，后续更短的同正文仍可被选中。

这不是语义去重：否定、时间差异、内部空白差异及不同细节仍保留。token 预算沿用已有“正文估算值累加”口径，不宣称覆盖最终提示词的包装、分隔符或模型真实 tokenizer。

### 3. 非有限参数与换算溢出

`memorySearchOptions` 对非有限 topK 返回 0；token 预算为 NaN、无穷或非正有效整数时不注入。半衰期先换算毫秒再检查有限性，避免 `Number.MAX_VALUE` 等有限天数溢出成 Infinity。正常配置值及正数取整行为不变。

## 合成基准（不是端到端收益）

[基准脚本](../scripts/benchmark-memory-retrieval.mjs) 只创建合成数据，不读取剧情。两版共用现有 tokenizer；测量前断言结果一致。10,000 条文档、20 次预热、5 组各 50 次查询，交替两版测量顺序，报告每次查询的组内平均耗时之中位数。索引构建、磁盘读取、归档遍历、模型请求不计入。

本地 Node 22.16.0 一次测量：

| 查询场景 | 修改前 | 修改后 |
| --- | ---: | ---: |
| 20 个词各命中 10 条文档（稀疏） | 3.798 ms | 0.044 ms |
| 一个共同词命中全部文档（稠密） | 2.028 ms | 1.976 ms |

稀疏查询有明显收益；稠密结果基本持平，细小差异可能来自 JIT/GC 与测量噪声。不据此声称整段对话或真实剧情提高相同倍数。

## 下一阶段建议（未在本次实现）

### 优先：候选数量与最终注入条数分离

[pipeline](../src/node/pipeline.ts) 目前先以 `retrievalTopK` 检索，再按 token 预算挑选。即使这次过滤掉重复正文，排在 topK 之外的独立事实仍无法补位。建议引入有上限的候选超取，再做精确/来源多样性筛选和预算选择，最后限制实际条数。需要同时衡量预算后的事实覆盖率、来源重复率和查询延迟；不能只把 topK 调大而取消预算。

### 优先：区分事实时间、编辑时间和摘要生成时间

[MemoryStore](../src/state/memory.ts) 用 `updated` 做时间衰减，归并经 `write` 产生新的当前时间戳。旧事实因重新摘要而获得较新的时间权重，是值得用剧情样例评估的排序风险，不代表所有现有摘要都错误。

建议为事件/事实时间保留独立字段或范围；摘要按来源传递事实时间，而不是把生成摘要时间当作事件发生时间。稳定设定、阶段事件和可被新事实替代的当前状态也应分开建模。引入 `supersedes` 等关系前，需要明确分支继承、编辑、删除和 WAL 回滚语义，不能用相似度直接覆盖“北门已开”与“北门未开”。

### 后续：主题化压缩与召回评测

[memoryMaintenance](../src/node/memoryMaintenance.ts) 当前选择最旧一批正文并要求压缩到 200 字以内。来源仍保留，但不同主题混合与多代摘要可能降低摘要视图的信息密度。可评估按事件/实体分组、限制每次输入 token、保留事实清单与来源标识，同时保持正常完成才归档、冲突校验和来源可回滚。

先建立匿名/手写剧情评测集，覆盖别名、指代、换种说法、旧事实被新事实替代、摘要丢细节及分支回退；关注预算后的事实覆盖率与错误旧事实泄漏。若这些评测显示词面召回不足，再评估可选混合检索，必须沿用 storyId 隔离、来源可达性和失效规则，不直接增加一个跨剧情共享向量库。
